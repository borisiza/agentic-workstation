- (decision) Scope locked to poc-plan.md Phases 0-8 (discovery through minimal security); Phases 9-10 (Firebase portal, Oracle migration) moved to Vision/Roadmap, not PoC requirements
- (decision) Codex Remote Control and Claude Code Remote Control are provider capabilities agentic-workstation configures/orchestrates, not features it reimplements; Codex Remote Control requires an early technical spike to confirm compatibility (Codex version, Mac arch, ChatGPT plan, mobile app, pairing, suspend/restart behavior) before being treated as a locked requirement
- (decision) Single primary actor for this PoC: Local Developer / Workstation Owner. One end-to-end journey plus 4 short secondary journeys (interrupted session recovery, cross-workspace access attempt, provider unavailable/unauthenticated, Mac suspend/restart). No standalone persona section.
- (decision) Workspace model: user-defined workspaces (not a fixed personal/publea/sandbox taxonomy) with minimum fields: stable id, name, authorized root path, allowed providers, permission config, non-sensitive metadata, enabled/disabled state. Test workspaces use fictitious names workspace-a/workspace-b.
- (assumption) Session = combination of provider + process + workspace + local non-sensitive metadata; no remote backend session concept in PoC
- (assumption) tmux/launchd/native daemons are persistence candidates to be evaluated in Phase 6, not a closed decision
- (assumption) Git remote is the source of truth for code; no uptime SLA for the local Mac PoC; suspend/sleep/network loss documented as known limitations
- (decision) Working mode: Coaching path, entry point Vision + Features (capability-first)
- (decision) D1 reframed: doctor.sh classifies tools as Required (macOS+arch compatible, Git, Claude Code adapter, Codex adapter, compatible shell, outbound HTTPS) vs Optional/installer-or-candidate (Homebrew=install mechanism, Node.js=only if actually needed, tmux=persistence candidate pending Phase 6 spike, Docker=optional/future hardening). doctor.sh must run and report even when dependencies are missing; missing deps block only the specific capability, never the diagnostic itself.
- (decision) D2 reframed: requirement is 'a secure system mechanism exists to store/reference credentials without persisting them in repo, workspace config, or logs' -- macOS Keychain is the preferred candidate to investigate, not a locked choice. Must also evaluate whether Claude Code/Codex already manage their own credentials securely; agentic-workstation must not read/export/centralize provider tokens unless indispensable.
- (decision) D3 split into D3-A (Anthropic account eligibility for Claude Code Remote Control) and D3-B (ChatGPT account eligibility for Codex Remote Control); failure of one must not block validating the other. Each adapter reports one of: available, not_installed, authentication_required, plan_not_supported, remote_control_unavailable, version_incompatible, network_unavailable, unknown_error.
- (decision) Primary outcome split into Product-controlled success (workspace registry/validation, adapter common contract, session start/status/stop/recover, isolation, security, diagnostics, reproducible docs) vs Provider-dependent qualification (Remote Control validated per provider, mobile app/pairing, eligible account/plan, external service availability). Core product can be judged technically correct even if one provider is externally blocked, provided the block is detected, explained, not papered over with a custom replacement, the other provider stays functional, and the block is logged as an external risk.
- (decision) Metric reworded from '2/2 providers operable via uniform commands' to '2 adapters implement a common contract for doctor/start/status/stop/recover, preserving each provider's specific capabilities and errors.' Uniformity applies to basic session lifecycle only, not all internal functions.
- (decision) Added success metrics: (9) doctor correctly identifies required/optional deps and per-provider blockers; (10) a failure in one provider does not prevent operating/diagnosing the other; (11) every session traces to exactly one provider and one workspace; (12) every isolation-rejected operation produces an explicit, auditable, secret-free error.
- (decision) Provider update notices (e.g. 'brew upgrade claude-code@latest') detected by doctor.sh are recorded as discovery findings only, never auto-executed. A separate controlled update procedure/story records current version, checks changelog/compatibility, performs the update, re-verifies auth+Remote Control, and documents rollback if a regression appears.
- (decision) NFR-2 (SSH keys-only) marked Deferred to Oracle Cloud PRD -- ID kept stable, not applicable to local-Mac PoC using native Remote Control
- (decision) FR-10 narrowed to logical isolation only (canonical paths, boundary validation, path traversal rejection, symlink-escape detection, no cross-workspace metadata/config/command mixing, rejection logging); added FR-10A: doctor reports effective isolation level per provider as logical/provider_sandboxed/os_enforced/unknown. Zero-cross-workspace-leak metric scoped to the defined acceptance test set, not an absolute guarantee against arbitrary user-privileged processes.
- (decision) Added concrete isolation acceptance tests: reject ../workspace-b, reject absolute path outside workspace, reject internal symlink escaping workspace, metadata separation across simultaneous sessions, workspace-a session cannot operate on workspace-b via agentic-workstation commands, result distinguishes wrapper-level block vs real provider/OS-level block
- (decision) FR-20/FR-21 reworded from 'configures and exposes' to 'invokes, supervises and diagnoses' native Remote Control using only public/documented provider interfaces -- no internal APIs, private files, or undocumented protocols
- (decision) FR-22 reclassified out of FR set into EQ-1 (mobile qualification scenario, provider-dependent, not a product requirement to build); unavailable mobile UI actions are logged as limitations, never auto-converted into agentic-workstation features
- (decision) Added FR-30 (>=2 simultaneous sessions across different workspaces, no ID/metadata/dir/lifecycle-command collisions; same-provider concurrency only if the provider supports it, else diagnosed)
- (decision) Added FR-31 (doctor generates compatibility/support matrix: macOS, arch, provider versions, install method, verified capabilities) and NFR-11 (PoC officially supported only on the validation Mac; other macOS versions/architectures considered supported only after passing the qualification suite there)
- (decision) Added NFR-12 (data-flow transparency: docs must state what stays on the Mac vs what Anthropic/OpenAI may transmit/store via auth, models, Remote Control) and FR-32 (before enabling Remote Control, user can view the external dependency, auth mechanism, and a link to the provider's applicable policy/docs) -- no legal consent flow required, but no false all-local claim either
- (decision) FR-24 conditioned on per-provider persistence spike outcome: only claim persistence via a supported/documented interface per provider; if a provider requires foreground process or has restrictions, adapter reports it as a limitation, never simulates a fake 'running' state. Added FR-24A: status detects dead processes / stale metadata, avoids reporting nonexistent sessions as active.
- (decision) IDs kept stable across the whole review cycle: FR-10A, FR-24A, FR-30, FR-31, FR-32 added as new IDs; EQ-1 tracked as a separate qualification-scenario namespace, not merged into FR numbering; no FR/NFR renumbered or reused
